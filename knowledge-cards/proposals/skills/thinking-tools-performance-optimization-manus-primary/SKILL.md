# 八工具效能最佳化

## 目標

把「感覺很慢、成本太高、問題反覆發生、不知道從哪裡開始」轉成可驗證的改善實驗。核心規則是：**先定義問題，再用證據定位；一次改一件事；改完重新測量；沒有改善就撤回。**

不要把八種工具全部機械套用。依問題選擇必要工具，最後一定收斂成：根因、假設、行動、驗證指標、回退條件與後續防護。

## 八種工具與適用時機

| 工具 | 要問的問題 | 最適合的用途 | 主要產出 |
|---|---|---|---|
| **5 個為什麼** | 為什麼會發生？再往下追到哪個可動手改的原因？ | 反覆故障、表面症狀、根因追查 | 根因鏈與第一個可修正點 |
| **第一性原理** | 哪些是事實？哪些只是慣例、假設或歷史包袱？ | 覺得「只能這樣做」、架構卡住、成本過高 | 不依賴慣例的重設方案 |
| **逆向思考** | 怎麼做一定會失敗、變慢或造成事故？ | 風險盤點、品質防線、避免錯誤最佳化 | 反模式清單轉成檢查表 |
| **事前驗屍** | 假設半年後計畫失敗，最可能的原因是什麼？ | 大型變更、遷移、上線與資源投入前 | 依風險排序的預防行動 |
| **六頂思考帽** | 事實、感受、風險、機會、創意、結論各是什麼？ | 團隊爭論、視角單一、需要平衡決策 | 分離觀點後的共識決策 |
| **二階思考** | 做完後會發生什麼？三個月或一年後呢？ | 快速修補、快取、降規、流程改造 | 一階／二階副作用與時間軸 |
| **MECE 拆解** | 是否互不重疊且完整涵蓋？哪一塊尚未檢查？ | 問題太大、不知從哪下手、漏查 | 可排序的問題樹與責任範圍 |
| **類比思考** | 其他產業怎麼解同類問題？哪些原理可搬用？ | 缺乏新方向、跨域設計、尋找成熟模式 | 可移植原理與適用限制 |

## 標準工作流程

### 1. 定義問題與成功條件

先寫出可觀察的問題，不使用只有「體感很差」的描述。

- 對象：哪個頁面、API、流程、設備、服務或決策？
- 症狀：慢、錯、貴、浪費、等待、重工或不穩定？
- 基準：目前數值、樣本、環境、時間範圍與資料來源。
- 目標：例如 p95 延遲、失敗率、工時、成本或恢復時間要改善多少。
- 限制：正確性、安全、資料新鮮度、預算、相容性與可接受風險。

若沒有基準，先標示 **UNKNOWN**，不要假裝已證明瓶頸。

### 2. 用 MECE 建立問題樹

把大問題拆成 3–5 個互不重疊、合起來足以涵蓋的方向。例如「API 變慢」可拆成：

1. 請求進入前：DNS、網路、TLS、佇列。
2. 應用程式：CPU、記憶體、鎖、序列化、外部服務。
3. 資料層：查詢計畫、索引、N+1、連線池、資料量。
4. 輸出與客戶端：payload、渲染、快取、重試。
5. 觀測與環境：部署差異、流量形狀、監控缺口。

逐塊標示「已測量／待測量／不適用」，避免只修最熟悉的區域。

### 3. 用第一性原理與 5 個為什麼找根因

先把每個結論分成：**事實、假設、推測、未驗證**。對主要症狀連問「為什麼」，直到得到一個可以透過程式、設定、流程或資源配置改變的原因；不要停在「使用者很多」或「系統本來就這樣」。

同時追問：

- 這是物理／業務限制，還是歷史慣例？
- 哪些步驟真正產生價值，哪些只是重複、轉換或等待？
- 能否減少工作量、縮短路徑、平行化、延後非必要工作，或直接移除工作？

若 5 個為什麼產生多條因果鏈，保留分支，不強行捏成單一根因。

### 4. 用逆向思考與事前驗屍建立防線

先反過來列出「一定會失敗」的做法，例如：

- 沒有基準就改架構。
- 只看平均值，忽略 p95／p99 或最差情境。
- 為了速度移除必要驗證、權限檢查或錯誤處理。
- 快取鍵漏掉租戶、語系、權限或功能旗標。
- 增加索引、執行緒或連線池，卻未確認資源代價。
- 一次合併多個變更，導致無法歸因。

再假設「半年後這個方案失敗」，列出至少 5 個原因，依發生機率與影響排序。每個高風險項目都要配一個現在即可做的預防動作、監控訊號與觸發回退條件。

### 5. 用六頂思考帽分離討論

在團隊或多方案比較時，依序整理：

- **白帽：** 目前有什麼數據、限制與未知？
- **紅帽：** 使用者、維運者或團隊的直覺擔憂是什麼？把感受標成感受，不當成事實。
- **黑帽：** 失敗模式、風險、相容性與安全代價。
- **黃帽：** 可量化的收益與成功條件。
- **綠帽：** 至少提出 3 個替代方案，不只在原方案上微調。
- **藍帽：** 收斂成決策、負責人、下一步與驗證時間。

不要讓「誰的職位較高」取代證據，也不要把紅帽的疑慮刪掉；它們應轉成可驗證的風險假設。

### 6. 用二階思考評估副作用

對每個候選方案至少寫出：

- 立即效果：延遲、成本、可靠性或工時如何變化？
- 下一層效果：流量增加、資料過期、維護複雜度、資源競爭或使用者行為會如何變？
- 時間軸：今天、三個月後、一年後各可能發生什麼？
- 反制：如何監控、限制、失效安全或回退？

尤其審查快取、非同步化、降級、批次化、重試、刪除驗證與擴大資源等「看似直接有效」的手段。

### 7. 用類比尋找候選方案，但驗證邊界

把問題改寫成通用句子，例如「如何在不犧牲正確性的前提下，減少大量重複等待？」再尋找 3 個不同產業或系統的解法。對每個類比記錄：

1. 原場景解決了什麼約束？
2. 可搬移的原理是什麼？
3. 本場景哪些前提不同？
4. 最小可行實驗如何驗證？

類比只產生假設，不是證據；不得因為知名公司採用就直接複製。

### 8. 實驗、驗證與防回歸

採用「測量 → 定位 → 單一修正 → 重新測量 → 保留或撤回 → 加入防護」循環。

- 使用與基準相同的環境、流量、資料量、快取狀態與測量方式。
- 一次只改一個主要變數；若不能拆開，先分別做隔離測試。
- 重複測量，區分真改善與自然波動。
- 正確性、資安與資料新鮮度是硬門檻；效能變好但功能錯誤仍算失敗。
- 結果在噪音範圍內、變差或測試失敗：撤回，不以「至少沒更糟」為理由保留。
- 對保留的變更加入測試、效能預算、監控、告警或定期檢視。

## 快速路由

- **反覆發生的錯誤：** MECE → 5 個為什麼 → 逆向思考 → 實驗。
- **系統或流程明顯變慢：** MECE → 測量 → 第一性原理 → 針對瓶頸實驗。
- **大型變更或遷移：** 第一性原理 → 事前驗屍 → 二階思考 → 小規模驗證。
- **團隊爭論方案：** 白帽 → 黑帽／紅帽 → 黃帽／綠帽 → 藍帽決策。
- **不知道有哪些解法：** 類比思考 → 第一性原理 → 小型實驗；不可只引用類比當結論。
- **修補看似有效但可能埋雷：** 逆向思考 → 二階思考 → 回退方案 → 監控。

## 效能工程常見檢查點

依症狀選擇，不要全做：

- 前端：LCP、INP、CLS、長任務、bundle、圖片尺寸與格式、渲染重複。
- 後端：p95／p99、CPU、記憶體、GC、鎖、外部依賴、重試與逾時。
- 資料庫：查詢日誌、`EXPLAIN ANALYZE`、N+1、索引選擇性、分頁、連線池。
- 快取：命中率、鍵完整性、TTL／失效策略、資料新鮮度、快取雪崩與 stampede。
- 可靠性：錯誤率、佇列深度、降級行為、回退時間與資料一致性。

不要因看到「慢」就直接加索引、加快取、加連線池或拆服務；先以測量證明該手段對應實際瓶頸。

## 禁止事項

- 未測量就宣稱找到瓶頸。
- 把八種工具當成必須逐一完成的儀式，造成分析本身成為浪費。
- 把類比、直覺或權威案例當成當前環境的證據。
- 只報平均值、只報成功案例，或隱藏被撤回的實驗。
- 以效能名義犧牲正確性、資安、權限、可觀測性或必要資料新鮮度。
- 保留沒有可測量收益、卻增加永久維護成本的複雜度。
